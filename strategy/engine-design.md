# 问鹤 · 推算引擎设计

> 目标：把传统术数里"可计算"的部分，做成一套**确定性、可测试、可追溯**的引擎。
> 非目标：不做事件预测；不让模型参与计算；不追求"全门派覆盖"。

---

## 一、总原则

1. **算、说分离**：引擎只算，模型只说。
2. **纯函数**：同样的输入永远得到同样的输出，不读网络、不读时钟（时间由调用方传入）。
3. **一切可追溯**：每个结论都能追到「规则 ID + 出处 + 引擎版本」。
4. **流派是配置，不是分叉**：换流派改配置，不改代码。
5. **零依赖**：纯 JS，浏览器和 Node 都能跑（离线包复用）。

---

## 二、分层

```
┌────────────────────────────────────────────┐
│ 0. 适配层 adapter                          │
│    浏览器 / Node / 离线包 → 统一调用接口     │
├────────────────────────────────────────────┤
│ 1. 历法 calendar                           │
│    公历⇄农历、节气、干支、真太阳时、夏令时    │
├────────────────────────────────────────────┤
│ 2. 排盘 chart                              │
│    四柱 / 小六壬 / 八宅 / 三合 / 建除        │
│    → 结构化命盘（chart.v1）                 │
├────────────────────────────────────────────┤
│ 3. 规则 rules                              │
│    条件表达式 + 判定 + 依据 + 置信度         │
├────────────────────────────────────────────┤
│ 4. 评分 score                              │
│    择日打分、合盘评分、相法评分              │
├────────────────────────────────────────────┤
│ 5. 解释 interpret（不在引擎内）             │
│    LLM 读取结构化结果，生成人话              │
└────────────────────────────────────────────┘
```

**引擎到「4. 评分」为止。第 5 层是服务端的事，引擎不依赖模型。**

## 五、规则 DSL

### 单条规则

```json
{
  "id": "face-shape-wood",
  "version": "1.0",
  "scope": "face",
  "when": {
    "all": [
      { "field": "measures.faceWH", "gte": 1.5 }
    ]
  },
  "then": { "field": "features.shape", "value": "wood" },
  "basis": ["sx-st-01"],
  "priority": 10,
  "confidence": 0.8,
  "school": "common",
  "reason": "脸长宽比 ≥ 1.5"
}
```

### 条件语法

| 操作 | 写法 |
| --- | --- |
| ≥ / ≤ | `{ "gte": 1.5 }` / `{ "lte": 0.3 }` |
| 区间 | `{ "between": [1.3, 1.5] }` |
| 枚举 | `{ "in": ["wood", "fire"] }` |
| 与 | `{ "all": [ ... ] }` |
| 或 | `{ "any": [ ... ] }` |
| 非 | `{ "not": { ... } }` |
| 比值 | `{ "ratio": { "a": "measures.cheekWidth", "b": "measures.jawWidth", "gte": 1.12 } }` |
| 存在 | `{ "exists": true }` |

### 匹配规则

1. 同一字段 **priority 高者优先**，其次按规则顺序
2. 命中后写入 `provenance`
3. 置信度 = 规则置信度 × 条件覆盖度
4. **没有规则命中时，不猜**——留给解释层说"这部分看不到"

## 六、评分模型

### 择日

```
score = 50
      + Σ 宜（+5 ~ +15）
      - Σ 忌（-5 ~ -15）
      - 冲主命（-20）
      + 吉神（+5）
clamp(score, 0, 100)
```

输出前 3 名 + 每条的理由（哪个宜、哪个忌、依据）。

### 合盘

```
score = 50
      + 日干合 +12
      + 日支合 +12
      - 日支冲 -15
      + 五行互补 +8 × n
clamp(score, 20, 96)
```

### 相法

```
score = 50
      + 各维度规则加权
      - 缺失维度扣分
```

**评分不是"好坏"，是"这套体系下的匹配度"。** 文案里必须写清楚。

## 七、可追溯与版本

| 版本 | 存在哪 | 作用 |
| --- | --- | --- |
| `engine.version` | 代码 | 算法变了要升 |
| `engine.rules` | 规则库 | 规则变了要升 |
| `conventions.school` | 每次输出 | 流派配置 |
| `tzdata` | 历法库 | 时区/夏令时数据 |

每个输出都带这四个版本号，用户能看到"这条结论是哪套规则算的"。

## 八、测试策略

### 1. 黄金样本（最重要）

`fixtures/charts/*.json`：输入 + 期望输出。每次改引擎跑一遍。

必须覆盖的边界：

- 立春前后一天
- 23:00 换日
- 闰月
- 1986–1991 夏令时
- 乌鲁木齐 vs 北京（真太阳时跨时辰）
- 时辰未知
- 1900 / 2100 边界

### 2. 属性测试

- 幂等：同一输入跑两次，`deepEqual`
- 纯函数：不读 `Date.now()`、不读网络
- 输出合法：符合 `chart.v1` Schema

### 3. 规则测试

- 每条规则至少 1 个通过用例、1 个不通过用例
- 每条 `basis` 必须能在古籍库里找到
- 同一字段的规则不能有"无优先级的重叠"

### 4. 回归测试

每次部署前跑全量；失败即回滚（已有 `deploy/rollback.sh`）。

## 九、性能与部署

- 引擎体积目标：< 200 KB（不含农历表）
- 排盘耗时目标：< 5 ms
- 浏览器可用：离线包直接 import
- Node 可用：服务端直接调用

## 十、迁移计划

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| P1 | 抽出 `calendar/`（干支、节气、真太阳时、DST、农历） | 纯函数 + 测试 |
| P2 | 抽出 `chart/`（四柱、小六壬、八宅、三合、建除） | `chart.v1` 输出 |
| P3 | 通用化 `rules/`（DSL + 引擎），迁移相法规则 | 规则库 v1 |
| P4 | `score/` + 黄金样本 100 例 | 测试集 |
| P5 | 服务端改为调用引擎，旧 `tools.mjs` 退役 | 版本对齐 |

**每阶段独立可上线，不搞大爆炸重写。**

## 十一、取舍与风险

| 风险 | 应对 |
| --- | --- |
| 流派争吵 | `conventions.school` 配置化，输出写明采用哪派 |
| 阈值没依据 | 标注"本产品规则"，不冒充经典；后续用样本校准 |
| 规则无限膨胀 | 每条规则必须有出处；无出处的只作"提示"，不作判定 |
| 模型跑偏 | 引擎输出结构化结论，模型只能润色，不能改判 |
| 性能 | 纯函数 + 查表，避免重复计算 |

## 十三、一句话

> **引擎不追求"算得神"，追求"算得清楚"。**
> 清楚 = 可复现、可追溯、可解释、可回滚。
