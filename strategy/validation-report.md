## 二、发现的缺陷

### 缺陷 1（严重）：日柱公式符号反了

原代码：

```js
const idx = (((54 - days) % 60) + 60) % 60;   // 错
```

正确：

```js
const idx = (((54 + days) % 60) + 60) % 60;   // 对
```

**影响**：除 2000-01-01（days=0）外，**所有日期的日柱都是错的**，连带时柱（时干由日干推）、大运、流日、合盘全部错。

**量化**：1950–2030 区间，仅 `days % 30 === 0` 的日期碰巧正确，约 **96.7% 的日期日柱错误**。

**为什么之前没发现**：所有测试都围绕"同一天输入 → 同一天输出"，没有和独立实现对照。**自洽不等于正确。**

### 缺陷 2：节气边界丢分钟

- 旧实现把出生时间取整点（`hourMid = floor(minutes/60)`）再和节气比
- 节气时刻精确到秒，例如 1965 芒种是 06:02:06
- 结果：06:00–06:02 出生的人被误判进午月

**影响**：节气当天 ±若干分钟出生的人，月柱甚至年柱（立春）错。

### 缺陷 3：节气时间本身有误差

旧实现用简化太阳黄经算法：

- 平均误差 **约 2 分钟**
- 最大误差 **约 13 分钟**

叠加缺陷 2，边界误差可达十几分钟。

### 缺陷 4：`conventions` 声明了 23:00 换日，但代码没实现

- 批注里写「23:00 起算子时」
- 实际日柱没有按次日算

**影响**：23:00–23:59 出生的人，日柱、时柱、起运全错一天。

### 附带：大运起运也用近似节气

起运距离按近似节气算，可能偏差几天，折算成起运岁数偏差 1–2 个月。

## 四、验证结果

```
cases: 6567   all-ok: 6567   100.00%

```

### 关于夏令时的 40 例差异

修复前剩余 40 例差异全部是 **1986–1991 夏令时的 23:30**：

- 我们：23:30（夏令时）→ 减 60 分钟 → 22:30 → 亥时，不换日
- lunar-javascript：不认识中国夏令时，按 23:30 算 → 子时，换日

**这是我们的处理更正确。** 校验脚本对夏令时样本先换算成标准时间再对账，因此 100% 一致。

## 五、对产品的影响（必须处理）

### 1. 历史数据全部受影响

- **所有已生成的命理/合盘/流日批注，日柱都是错的**
- 记录存在用户浏览器 localStorage，服务端没有副本，**无法批量修正**
- 相法、择日、堪舆不受影响（不依赖日柱）

### 2. 建议处理

| 动作 | 说明 |
| --- | --- |
| 加版本号 | 批注写入 `engineVersion`，旧记录标记"旧版算法" |
| 加"重新生成" | 旧批注页提供一键重算 |
| 公告 | 坦承修复，说明原因——**这是加分项，不是减分项** |
| 清演示数据 | 内部测试记录建议清空 |

### 3. 信任层面的意义

这次校验证明了一件事：

> **"可核对"不是口号，是能抓出自己错误的机制。**

建议把校验脚本和报告公开（或写进关于页），这比任何"祖传秘法"都更能建立信任。

## 七、教训

1. **自洽 ≠ 正确**：自己和自己比，永远发现不了系统性错误
2. **边界值必须用独立实现对照**：节气、换日、闰月、夏令时
3. **声称的约定必须落到代码**：`conventions` 写了 23:00 换日，代码没做，就是撒谎
4. **精确表比算法更可靠**：90 KB 的节气表，胜过任何简化公式
